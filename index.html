Local inference hardware / Prices checked 1 Nov 2026

Every rig is short of bandwidth or usable memory

Token generation is memory-bandwidth-bound, and the size of the model sets the minimum memory you need. Those two numbers determine almost everything else, and none of the hardware options here offers plenty of both at a reasonable price. What you are really buying is memory. At current prices, every M5 Ultra configuration costs about $52 per gigabyte of usable memory, versus $70 for a DGX Spark and $188 for an RTX 5090. This page compares eleven ways to run models locally on memory, speed, long-context behavior, software and price, and ends with a recommendation for each priority.

Software support, and the catch

The R9700 is better supported than AMD's integrated chips. AMD defines ROCm support one GPU design at a time, and gives each design a code name. The integrated GPU in Strix Halo is gfx1151, and AMD's software problems are worst there: Vulkan beats AMD's own ROCm by 2.5×, and PyTorch needs community support. The R9700 uses a different design, gfx1201, and AMD lists it as officially supported by ROCm 7.2 on Linux and Windows. ROCm ships ready-made GPU code for it, so you do not need the HSA_OVERRIDE setting that makes ROCm treat an unsupported chip as a supported one.

Official support still does not mean parity with CUDA. The fastest measured llama.cpp result on this card was on Vulkan, not ROCm (127 tok/s, or 156 with AMDVLK and a patch). Ollama ships ROCm 6.x libraries that have no gfx1201 kernels, so its GPU discovery times out and it falls back to the CPU until you set OLLAMA_VULKAN=1. You still have to choose a backend for each model, rather than install one thing that works.

Prefill rules it out for long-context work. The R9700 processes a 512-token prompt at 2,713 tok/s versus the 5090's 7,026, and the gap widens to 3.44× at 32K. Agents, retrieval over documents and long chats all send a long context with every request, so for them prefill is the speed that you notice most, and it is where this card is weakest. It is a good low-cost card for short prompts and batch jobs, and a poor one for long-context work.

Context, which changes all of the above

Every number in the matrix is measured starting with an empty context: the model generates right after a very short prompt. That keeps the KV cache from adding to the memory that each token reads, so the differences between columns come from the hardware alone, which makes it the fairest comparison across machines. Real use almost never looks like that. A chat re-sends the whole conversation with each message, and agents and document retrieval add long tool outputs and documents on top, so context adds three separate costs. You need memory to hold the KV cache, you wait for prefill before the first token, and decoding slows down, because attention reads the entire cache for every new token.

The non-obvious part

MoE models slow down more with growing context than dense models do.

To write each token, a model reads two things from memory: the weights that it uses for that token, and the KV cache for the context so far. The weights are the same size for every token, but the cache grows with the context. A dense model reads all of its weights for every token, so the cache adds only a small share to each read. An MoE model reads only its active parameters, so the same cache adds a much larger share. Decode speed depends on how much is read, so reading 44% more per token makes each token take 1.44 times as long, and speed falls by 31% (1 ÷ 1.44 = 0.69). At 32K tokens of context:

  • gpt-oss-120b (MoE) reads about 2.7 GB of active weights per token, plus about 1.2 GB of cache. That is 44% more reading, so the arithmetic predicts a 31% drop. The Spark measured 33%
  • A dense 70B model at Q4 reads about 40 GB of weights per token, plus about 10.5 GB of cache. That is 26% more reading, so the arithmetic predicts a 21% drop

The M5 Ultra lost less than the arithmetic predicts on gpt-oss-120b, 20% in a measured run, so treat these figures as a guide. The Spark is strongest on MoE models, and growing context erodes that strength fastest.

Two Sparks or one Mac

Two Sparks cost ~$15,400 and give you about 220 GB of usable memory at about 365 GB/s of effective bandwidth. A 256 GB M5 Ultra costs ~$12,000 and gives you about 230 GB at 1,200 GB/s. The Mac is $3,400 cheaper, with slightly more memory and 3.3× the bandwidth.

The 512 GB Mac, at ~$24,750, is in a different budget. At the Spark pair's price, the fair comparison is the 256 GB machine, and the pair loses to it on every hardware measure in the tables above.

CUDA is the one real argument for the Spark. The Mac has no upstream vLLM, no NVIDIA container stack, and a much smaller fine-tuning ecosystem. If you need to develop against the same stack that you deploy to, a single Spark is still worth buying. A second one is not.

Clustering: does a second box buy speed, or only memory?

macOS Tahoe 26.2 added an RDMA driver for Thunderbolt 5, which lets one Mac read another's memory directly (Thunderbolt 5 is rated at 80 Gb/s, and RDMA traffic between Macs reaches about 50–60 Gb/s, or 6 to 7.5 GB/s, with under 50 microseconds of delay). That is far slower than each Mac's own memory, so a cluster only helps if the software sends little data across the link. Whether a second box adds speed, or only memory, depends on that software.

Two Sparks: the same rule applies

Two Sparks gain speed too, if the software splits every layer across both. The Sparks connect through their ConnectX-7 ports at 200 Gb/s, with RDMA built in. With layer splitting, as in llama.cpp, each layer still runs on one machine at a time, so the second Spark adds memory but no speed. With tensor parallelism in vLLM or TensorRT-LLM, both Sparks work on every layer at once and each reads half of the weights, so the pair is faster. These are the published single-request results:

  • gpt-oss-120b in vLLM: about 38 tok/s on one Spark and 52 on two with the standard release (+35%). Community-patched builds reach about 60 on one Spark and 81 on two (+33%)
  • Qwen3 235B at NVFP4 in TensorRT-LLM: 11.7 tok/s on two Sparks, measured by NVIDIA. The model does not fit on one Spark at this quantization

The two-Spark column in the matrix uses these results. Where no measurement exists, it applies the +33% from gpt-oss-120b, which puts the pair at about 365 GB/s of effective bandwidth. That is close to the +34% that two Macs gain with EXO.

What the measurements show

The runtime determines whether clustering helps at all. Compare rows one and three. With the same model, hardware and interconnect, EXO with RDMA gains 34% on two nodes, while llama.cpp loses 16%. If you add a second Mac and run the wrong software, the pair is slower than one machine. You cannot buy this as a hardware feature, you have to deploy it.

Very large MoE models run slower than the bandwidth formula predicts. The figures above are from M3 Ultra machines at 819 GB/s. Owners have published M5 Ultra measurements since it shipped, but none yet for these two models. Scaled by bandwidth, the M3 Ultra figures put a single M5 Ultra at about 31 tok/s on DeepSeek 671B and 29 on Qwen3 235B. The formula alone would predict about 48 and 50–80. These models reach well below the efficiency of mid-size models, most likely because expert routing scatters the memory reads. The matrix uses the scaled measurements.

Two 256 GB Macs cost less than one 512 GB Mac. The pair comes to ~$24,000 delivered and the single machine to ~$24,750. The pair is $750 cheaper, with 20 GB less memory and about 34% more throughput. The single machine is simpler: one box instead of two, and no dependence on EXO or the RDMA link.

The software each platform runs

These machines use four different software stacks. The stack determines what you can run, how soon after a model's release you can run it, and what else you can do besides inference. One thing is the same everywhere: every stack below exposes an OpenAI-compatible HTTP endpoint, so your applications talk to the machine the same way whatever you buy. The stack affects what happens on the box, not how you reach it.

Three conclusions about the stacks

The Spark's CUDA advantage is narrower than "it runs CUDA" suggests. It runs aarch64 CUDA on compute capability sm_121. NGC containers work, but many pip wheels do not. You will hit bugs that are specific to this compute capability, such as vLLM falling back from its fast FP4 code to slower general-purpose code, before most other users do, because few people own one. It is not a drop-in Linux CUDA box, and working around these problems takes real time.

The Mac is a very good inference machine and a poor platform for developing LLMs, including fine-tuning. MLX runs 20–40% faster than llama.cpp on the same chip. Upstream vLLM does not run on Metal, but the community vllm-mlx project reimplements the important parts: continuous batching, a paged KV cache and prefix caching. What the Mac lacks is the fine-tuning toolchain. PEFT, TRL, Unsloth and Axolotl are CUDA projects, and MLX's own LoRA tools are a separate ecosystem. If the job is serving models, the Mac is fine. If it includes conventional fine-tuning or running research code as published, it is not.

On AMD's integrated chips, the software cancels out the memory. On Strix-class hardware (gfx1151), the Vulkan backend beats AMD's own ROCm on llama.cpp prompt processing by about 2.5× (880 versus 350 tok/s on Llama-2-7B Q4_0). llama.cpp's ROCm backend is built on HIP, AMD's counterpart to CUDA, and on this chip it is barely faster than the CPU for prefill. AMD's math library for gfx1151 is several times less efficient than its versions for discrete GPUs, and PyTorch has no official builds for the chip, so it relies on community support. Gorgon Halo offers 160 GB for $3,999, the most memory per dollar of anything mentioned here, and it is still hard to recommend.

What this means for timing

The usual reason to wait is that something better is close. Nothing is.

Apple's next Studio is expected in 2028. NVIDIA has announced no Spark successor and is putting the GB10 chip into laptops. AMD's Gorgon Halo adds memory to 2025 silicon, and its real successor arrives in 2027 at the earliest. DRAM prices are rising, so waiting is likely to cost money rather than save it. The one interesting item on the horizon is LPDDR6. If Medusa Halo ships at 691 GB/s with a large memory pool, it breaks the trade-off between usable memory and bandwidth. But it is two years away and unconfirmed, so you cannot plan a purchase around it.

Where the $1,300 goes

The upgrade buys 25% more GPU cores and 20% more CPU cores. It buys no extra memory bandwidth, and bandwidth is the only thing that decode speed depends on.

Decode speed is the same in both bins. The 36/80 bin prefills about 25% faster, which saves about 3 seconds on every 32K-token prompt. Chats, agents and document work re-send a long context with every request, so that wait comes back on every turn. The 30/64 bin saves about $1,450 delivered, roughly 12% of the price, and it is a reasonable choice only if most of your prompts are short. For most LLM work the 36/80 bin is the safer buy, and every M5 Ultra price on this page is for it.

The same logic applies to storage. Apple charges $500 to go from 1 TB to 2 TB, which is $500/TB. A Thunderbolt 5 NVMe enclosure costs about $250, and Gen 4 drives cost about $100–130/TB during the NAND shortage. A 4 TB external drive therefore comes to about $175/TB. It reads at about 6,000 MB/s, roughly 80% of the speed of the Mac's internal SSD, so a 60 GB model loads in about ten seconds. Take the 1 TB internal drive and put the savings toward more memory.

Which one, and when

Start with the largest model that you need to run, because its size sets the minimum memory. Above that floor, more bandwidth means faster generation, and more compute means faster prefill on long prompts. Then check that the software stack runs what you need. Each recommendation below names the priority that it serves.

Recommended if value rules · ~$3,660

Dual RTX 3090

The only NVIDIA option under $5,000. Memory costs $76/GB versus the 5090's $188, and it runs a 70B dense model entirely on the GPUs, which the 5090 cannot. You pay for that with 700 W and a build that you have to design yourself.

If VRAM per dollar rules · ~$2,550

Radeon AI PRO R9700

32 GB for 42% of a 5090's price, at $80/GB versus $188. ROCm 7.2 supports it officially, unlike AMD's integrated chips. But prefill runs 3.44× slower than on a 5090 at 32K context, so it suits short prompts and batch jobs, not long-context work.

If latency rules · ~$6,000

Single RTX 5090

The lowest latency per dollar on models that fit in 32 GB. But it is the worst memory value here apart from the PRO 6000, and supply is thin enough that used cards sell above new ones. Buy it only if 32 GB really covers what you run.

If CUDA parity rules · ~$7,700

DGX Spark 128GB

The only machine here with the same architecture as a GB200 deployment target, and the cheapest CUDA machine that holds a 120B MoE model. At $70/GB it is not a memory-value buy. Buy it to match your deployment stack, not for the memory.

Avoid · ~$5,550

DGX Spark 64GB

Worse memory value than the 128 GB model ($101/GB versus $70), and its ~55 GB of usable memory will not hold gpt-oss-120b. It is a cheaper Spark that cannot do the job that people buy Sparks for.

Recommended, best all-round · ~$12,000

M5 Ultra 256GB

230 GB at 1,200 GB/s. It costs $3,400 less than two Sparks, with slightly more memory and 3.3× the bandwidth, and it ties for the best memory value on the page. You give up CUDA and the fine-tuning toolchain.

If one box matters · ~$24,750

M5 Ultra 512GB

480 GB in a single machine, running DeepSeek V3.2 at Q4 at about 31 tok/s. At $52/GB its memory is no cheaper than the 256 GB model's, and two of those cost $750 less with more throughput. Buy this because one machine is simpler to run, not to save money.

If frontier weights rule · ~$49,500

2× M5 Ultra 512GB

~960 GB, enough for Kimi K2.5 at a trillion parameters or DeepSeek V3.2 at Q8. It is the only option here that runs frontier open weights at full quality. At $49,500 this is a capital decision, not a hardware purchase. Requires EXO and macOS Tahoe 26.2.

Better than the 512 · ~$24,000

2× M5 Ultra 256GB

~460 GB, with about 34% more throughput than a single machine, for $750 less than one 512 GB machine. You give up 20 GB and take on the work of running a cluster. Unless you need everything in one box, this is the better way to spend $24,000.

Avoid · ~$15,400

2× DGX Spark 128GB

It costs $3,400 more than a 256 GB M5 Ultra, for about the same memory and less than a third of the bandwidth. At $42.19 per GB/s it is the worst bandwidth value on the page. Buy it only if you need more than 200 GB of memory on CUDA.

Terms used on this page

Definitions of the technical terms above, grouped by topic.

Speed

Token
A unit of text that a model reads and writes. An English word is about 1.3 tokens on average, so 1,000 tokens is roughly 750 words.
tok/s
Tokens per second. Unless a figure is labeled as prefill, it means generation speed: how fast the answer appears.
Batch size 1
One request handled at a time, as when one person chats with a model. Every speed on this page is for a single request at batch size 1. A server can also handle many requests together, as a larger batch. It then produces more tokens per second in total, because one read of the weights from memory serves every request in the batch. Each individual request runs a little slower.
Prefill
The first stage of answering, in which the model processes the whole prompt before it writes anything. Prefill is limited by compute, so it scales with GPU cores. It is also called prompt processing.
Decode
The second stage, in which the model writes the answer one token at a time. Each token requires reading the active weights from memory, so decode speed is limited by memory bandwidth. It is also called token generation.
Time to first token
How long you wait before the answer starts to appear. It is mostly prefill time, so it grows with the length of the prompt.

Context

Context
Everything that the model works with for a request: the prompt, the earlier conversation, and any documents or tool output. "32K" means about 32,000 tokens of context (32,768 exactly).
KV cache
The memory that holds the model's processed version of the context, so that the model does not reprocess the whole context for every new token. It grows with the length of the context and competes with the model's weights for memory.
Prefix caching
Reusing the KV cache for the part of a prompt that has not changed since the last request, such as a long system prompt or the earlier part of a conversation. It cuts the time to first token on follow-up requests.
Continuous batching
A server feature that adds new requests to a running batch as soon as there is room, rather than waiting for the batch to finish. It matters when several people or programs share one machine.

Models and quantization

Parameters, 70B
The learned numbers that make up a model, also called weights. "70B" means 70 billion parameters.
Dense model
A model that uses all of its parameters for every token.
MoE (mixture of experts)
A model that uses only part of its parameters for each token. gpt-oss-120b has 117 billion parameters but uses about 5.1 billion per token. All of them must fit in memory, but only the active ones are read for each token, so an MoE model generates much faster than a dense model of the same size.
Active parameters
The parameters that an MoE model actually uses for each token. Decode speed depends on these, not on the total.
Quantization
Storing each weight in fewer bits, so that the model takes less memory and generates faster, at some cost in quality. Open models are usually released at 16 bits per weight.
FP16, BF16
16-bit formats, the usual full size of an open model. A 70B model takes about 140 GB.
Q8
About 8 bits per weight, half the size of FP16: about 70 GB for a 70B model. Quality is very close to the original.
Q4
About 4 to 5 bits per weight, roughly a quarter of the size of FP16: about 40 GB for a 70B model. It is the usual choice for local use, with a small loss in quality. "Q4-class" means any format of about 4 bits. Names such as Q4_K_M are specific llama.cpp formats in this class.
Q3, Q2
About 3 and 2 bits per weight. They let a larger model fit in less memory, but quality drops noticeably, especially at Q2.
FP8, FP4
Floating-point formats that use 8 and 4 bits per number. A GPU with hardware support for a format runs it much faster than a GPU that has to convert it first. NVIDIA added FP8 support with its Ada and Hopper chips, and FP4 with Blackwell, which includes the RTX 5090, the RTX PRO 6000 and the DGX Spark. The RTX 3090 supports neither.
MXFP4, NVFP4
Two 4-bit formats that store one shared scale factor for each small block of weights, which keeps more accuracy than plain 4-bit numbers. MXFP4 is an open industry standard with one scale per 32 weights, and the gpt-oss models are released in it. NVFP4 is NVIDIA's version, with one scale per 16 weights.
GGUF, AWQ, GPTQ
Formats for quantized models. GGUF is the llama.cpp format and the most widely available. AWQ and GPTQ are 4-bit methods used mainly with vLLM.

Hardware

Usable memory
The memory available for the model and its KV cache. For a GPU it is the card's own memory (VRAM). For a unified-memory machine it is the total minus what the operating system needs.
Unified memory
A design in which the CPU and GPU share one pool of memory, as in the Mac Studio, the DGX Spark and AMD's Halo chips. It allows much more memory per machine than a GPU card, usually at lower bandwidth.
Memory bandwidth
How many gigabytes per second (GB/s) the chip can read from memory. It sets the ceiling on decode speed.
Effective bandwidth
For a pair of machines, the bandwidth that the pair delivers in practice, worked out from how much faster it runs than one machine.
Bin
One version of a chip, sorted by how many of its cores work. Apple sells the M5 Ultra with a 30-core CPU and 64-core GPU, or with a 36-core CPU and 80-core GPU ("36/80"). Both bins have the same memory bandwidth.
Delivered cost
Street price plus about 11% sales tax, plus a host PC for the GPU configurations.
Layer splitting, tensor parallelism
Two ways to split a model across GPUs or machines. With layer splitting, also called pipeline parallelism, each GPU holds some of the layers and the GPUs take turns, so you gain memory but not speed. With tensor parallelism, every layer is split across the GPUs so that they work at the same time, which is faster but harder to set up.
RDMA
Remote direct memory access. It lets one machine read another's memory directly over the cable that connects them, which cuts the delay when two machines share one model.
Thunderbolt 5, ConnectX-7
The links used to join two machines. Macs use Thunderbolt 5, rated at 80 Gb/s. The DGX Spark has a ConnectX-7 network port, rated at 200 Gb/s. Both support RDMA.
gfx1151, gfx1201
AMD's code names for two of its GPU designs. ROCm uses these names to decide which chips it supports. gfx1151 is the GPU built into the Strix Halo and Gorgon Halo chips. gfx1201 is the RDNA 4 GPU in the Radeon AI PRO R9700. Support for one says nothing about support for the other.
Strix Halo, Gorgon Halo, Medusa Halo
Generations of AMD's Ryzen AI Max chips, which put the CPU and GPU in one package with unified memory, like a Mac or a DGX Spark. Strix Halo launched in 2025, Gorgon Halo is its refresh with more memory, and Medusa Halo is expected in 2027 or 2028. The software tables call them "AMD Halo".
aarch64
The 64-bit Arm instruction set, used by the DGX Spark and by Macs. Most PC and server software is built first for x86, so some of it is missing or late on aarch64.
Compute capability, sm_121
NVIDIA's version number for a GPU's feature set. The DGX Spark's chip is sm_121, which few other machines share, so prebuilt software often lacks support for it.

Software

CUDA, ROCm, Metal, Vulkan
The programming platforms for NVIDIA GPUs, AMD GPUs, Apple silicon and (for Vulkan) GPUs from any vendor. Inference software has to support the platform that your hardware uses.
HIP
AMD's programming interface for its GPUs, part of ROCm. It closely follows CUDA's design, so that CUDA code can be ported to AMD. llama.cpp's ROCm backend is built on it.
MLX
Apple's machine-learning framework for Apple silicon. mlx-lm is its tool for running language models.
Inference engine
The program that loads a model and answers requests. llama.cpp runs almost everywhere, and Ollama is an easy-to-use wrapper around it. vLLM and SGLang are built to serve many requests at once, and TensorRT-LLM is NVIDIA's own engine. vllm-mlx is a community version of vLLM for Macs.
EXO
Open-source software from EXO Labs that runs one model across several Macs, using RDMA over Thunderbolt 5. The clustering section compares it with the alternatives.
PyTorch
The most widely used framework for training and running models. Most research code and fine-tuning tools are written for it, and they run best on CUDA.
Fine-tuning, LoRA, QLoRA
Further training of a model on your own data. LoRA trains a small set of added weights instead of the whole model, and QLoRA does the same on a quantized model to save memory.
Speculative decoding
A small draft model guesses the next few tokens, and the large model checks all of the guesses in one pass. It speeds up decode when the guesses are often right.

Method and confidence

Prices are delivered cost: street price plus about 11% sales tax (a US West Coast metro rate), applied to every configuration so that they compare fairly. Substitute your own rate. The GPU configurations also include a host PC, at about $500 before tax for a single-card build, $600 for a dual-card build and $1,500 for the RTX PRO 6000 workstation. Street prices were checked between 19 October and 1 November 2026. They are asking prices, not completed sales.

Pre-tax street prices. RTX 3090 used $1,350, new $1,550–$1,950. RTX 5090 new from $4,921 and used from $5,880, versus a $1,999 MSRP. Tom's Hardware has reported, without confirmation, that NVIDIA has stopped GB202 production for consumer cards. DGX Spark 128GB $6,950 and 64GB $4,999. RTX PRO 6000 $15,999–$16,000. Radeon AI PRO R9700 $1,800 a card, versus a $1,299 MSRP that no retailer charges. The lowest tracked US price was $1,827 on 26 October, and Amazon listings were near $1,700 in mid-October. The 12-month median is $1,460, and used listings start at about $1,907.

Mac Studio with M5 Ultra. It starts at $5,499 for the 30-core CPU / 64-core GPU bin with 96 GB and 1 TB. Upgrades cost $1,300 for the 36/80 bin, $4,000 for 256 GB and $500 for 2 TB. The configurator offers 256 GB with either bin: $9,499 with the 30/64 bin and $10,799 with the 36/80 bin, about $10,550 and $12,000 delivered. This page uses the 36/80 bin. The 512 GB model costs $22,299 with the 36/80 bin and 1 TB, about $24,750 delivered. Its memory option alone is $15,500. The first 160 GB above the 96 GB base cost $25/GB, and the next 256 GB cost $45/GB, so do not extrapolate Apple's memory prices in a straight line.

Prices are moving fast. Between late August and October 2026, NVIDIA raised the DGX Spark 128GB from $4,699 to $6,950, an increase of 48%. Used RTX 3090s rose 23% from $1,095–$1,181. The lowest new RTX 5090 price rose about 13% from $4,288–$4,381, and the RTX PRO 6000 rose from $13,998–$15,499. Apple has not changed its prices since the M5 Ultra launched on 25 August. Check current prices before you buy.

Performance. R9700 figures are measured llama.cpp results on a single card. It runs Qwen3.5-35B-A3B at 127.4 tok/s on Vulkan, or 156.3 when tuned, and Qwen3.5-27B dense at 29–33 tok/s. With a tuned ROCm build it runs Qwen2.5-Coder-7B at ~99 tok/s, and it prefills a 512-token prompt at ~2,713 tok/s. The dual-card figures are based on layer splitting, so decode speed matches a single card and only memory grows. The dual-card 70B figure is derived, not measured. The DGX Spark gpt-oss results are measured, and come from the llama.cpp benchmark thread. The RTX 3090 and RTX PRO 6000 results are measured, and come from published llama.cpp and Ollama runs. The M5 Max results at 614 GB/s come from hardware-corner's benchmark set, including gpt-oss-120b Q8 at 87.9 tok/s decode and 1,325 tok/s prefill. M5 Ultra figures for gpt-oss-120b and gpt-oss-20b are measured by owners with MLX on 256 GB machines: gpt-oss-120b runs at 110 tok/s in oMLX on the 80-core GPU, and at 120 in a separate MLX run that falls to 96 at 32K tokens of context. The other M5 Ultra figures are derived. Where no measurement exists, they are scaled from the M5 Max results by the 1.95× bandwidth ratio, since the Ultra is two Max dies. For gpt-oss-120b that scaling predicted about 170 tok/s, well above the measured 110–120, so treat the derived M5 Ultra figures as optimistic. Apple claims 4.3× the AI compute of the M3 Ultra, so prefill may beat the estimates. RTX 5090 speeds come from RTX PRO 6000 measurements, since both use the GB202 die at the full 1,792 GB/s. Other derived figures use tok/s ≈ bandwidth × efficiency ÷ bytes read per token. Treat every figure as ±20%.

Context figures. KV cache sizes are calculated from published model architectures (2 × layers × KV heads × head dim × bytes), not measured. They come to about 0.32 MB per token for a Llama-class 70B and 0.26 MB for a 32B. gpt-oss-120b needs only about 0.036 MB per token, because it uses grouped-query attention and half of its layers keep only a 128-token window. Time to first token is the context length divided by the prefill rate at that context length. The Spark's figures are measured: decode falls from 60.57 tok/s with an empty context to 40.55 with 32K tokens of context, and prefill falls from 1,956 tok/s to 1,027. The M5 Ultra's decode loss is measured too: gpt-oss-120b falls from 120 tok/s to 96, a 20% loss. The other columns apply the Spark's shape, because the slowdown depends mostly on the ratio of KV cache to weights.

Structural caveats. Dual-3090 speeds are based on llama.cpp layer splitting, where the cards work in turn and effective bandwidth stays at 936 GB/s. vLLM tensor parallelism reaches about 1.4–1.6× that, with a more fragile setup. Two-Spark figures are based on tensor parallelism in vLLM or TensorRT-LLM over the 200GbE ConnectX-7 link. The +33% for the pair comes from gpt-oss-120b in vLLM: about 60 tok/s on one Spark and 81 on two with community patches, and 38 versus 52 with the standard release. With layer splitting the pair adds memory but not speed. Multi-Mac figures come from four M3 Ultra Studios at 819 GB/s, scaled by bandwidth to the M5 Ultra. They require macOS Tahoe 26.2 for the Thunderbolt 5 RDMA driver and EXO as the runtime. They do not apply to llama.cpp, which gets slower as you add nodes. Batching and prefix caching on Apple silicon require the community vllm-mlx server, not mlx-lm or llama.cpp.
